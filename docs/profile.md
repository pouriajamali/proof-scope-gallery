# VC receipt profile 0.1.0

P0 decision: **GO — compose an existing verifier, do not build cryptography**.

Audience: a developer consuming a model service receipt who needs to distinguish
an authentic issuer statement from evidence about the requested computation.
Scenario: an authentic receipt for task B is presented as evidence for task A.

The repository was empty at P0 inspection. There is no baseline core to extend in
this repository. No private source, ledger, employer material, or handoff snapshot
is reused. Fixtures will be newly authored synthetic examples under MIT.

## One selected profile

`vc-jws-eddsa-receipt/0.1.0` uses the VC route only. The existing
[`jose` compactVerify](https://github.com/panva/jose/blob/v6.2.18/docs/jws/compact/verify/functions/compactVerify.md)
verifier performs the actual JWS signature check. Pin `jose` to **6.2.18** (MIT),
with npm lockfile integrity; Node.js 22.14+ supplies WebCrypto Ed25519.
No prover, ZK system, TEE, blockchain, model inference, or GPU is required.

The payload is an unsecured credential directly inside compact JWS, with protected
`typ: vc+jwt`, `cty: vc`, `alg: EdDSA`, and an absolute `kid`. The credential uses
the VC v2 context and a fixed local extension for a JSON service receipt.
`iss`, if supplied, must equal `issuer`. This is a deliberately constrained
application profile, **not a general VC conformance validator or certification**.
No remote JSON-LD expansion, DID resolution, credential status list, JWE, or SD-JWT
is implemented. Unknown credential features are rejected instead of ignored.

Sources: [W3C securing VCs, Recommendation 2025-05-15, §3.1.1 and §4](https://www.w3.org/TR/2025/REC-vc-jose-cose-20250515/),
[VC Data Model 2.0, verification definition](https://www.w3.org/TR/vc-data-model-2.0/#dfn-verify).

## Inputs and public output

Input: signed compact JWS; explicit offline issuer/key trust configuration;
expected request, model and code versions, input/output SHA-256 digests,
quote/charge, domain and nonce; verifier time; requested claim.
Only digests and synthetic public identifiers enter the receipt. Raw private
inputs are not included. Digests may still leak low entropy inputs; this profile
does not provide confidentiality or prevent dictionary attacks.

Output is structured, with separate statuses and reasons for:

1. Cryptographic signature verification against a configured public key.
2. Credential shape, issuer trust and validity interval policy.
3. Request/model/code/input/output/quote/charge/domain/nonce binding.
4. Requested claim scope, including explicit unsupported claims.

The raw verified public credential remains inspectable. A green signature is
never rendered as a green computation-quality result.

## Supported and unsupported claims

| Claim | Evidence / supported scope | Unsupported inference |
| --- | --- | --- |
| `issuer-statement` | Signature authentic under a locally configured key, accepted issuer and validity policy | Real-world identity, honesty, hardware isolation |
| `request-binding` | Verified public fields exactly match the caller's complete expected context | Issuer actually executed that request |
| `output-binding` | Supplied output bytes hash to the signed output digest | Output is correct, useful, licensed, or generated by that model |
| `correct-execution` | Unsupported by this VC profile | ZK or attested execution |
| `quality` | Unsupported | Truth, accuracy, safety, commercial quality |
| `data-rights` | Unsupported | Training/input/output ownership or permission |
| `hardware-attestation` | Unsupported | GPU usage, TEE provenance, SLA |
| `payment-settlement` | External evidence required | Payment or asset receipt proved by service receipt |

An execution claim in the receipt is labelled **issuer-asserted**. A quote or
charge is also an issuer statement and binding field, never settlement evidence.

## Trust and failure model

Trust the configured issuer-to-public-key mapping, WebCrypto/jose, caller-supplied
expected context, clock and any caller-managed replay store. Do not trust keys
embedded in a token or fetch key URLs from it. A compromised trusted signing key
can sign false statements. A caller that accepts the wrong expected context can
accept the wrong task. Offline local revocation/rotation is policy, not a global
live identity-status guarantee. Replay protection needs state at the relying party.

CPU-only examples should be small; actual runtime will be recorded at P2.
Installation needs npm access once; subsequent demo/test execution is offline.
No external audit, production security, inference quality, or AI advantage is claimed.

## Phase gates retained

P1: real signature and separate binding/scope negative tests.
P2: reproducible gallery, independent expected results and fresh install/CLI.
P3 / CMP-06: versioned offline service receipt and consumer adapters for G2/G3;
consume CMP-02/03 contracts only with explicit version/native semantics.
P4: compare claim classification against the deterministic checker with held-out
labels, attribution and cost; do not invent a model run or claim improvement.
P5: replay, domain, expiry, rotation/revocation, with invalid crypto vs binding
recorded separately. P6: independent consumer before a second profile, plus
maintenance/contribution evidence. No second profile is authorized by convenience
alone; evidence of independent consumption is the gate.
